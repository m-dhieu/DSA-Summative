# Embedded Device Event Logger

## Introduction
This application records, manages, navigates, and saves diagnostic events generated by embedded monitoring devices. It utilizes a **dynamically allocated doubly linked list** to manage event records.

---

## Design and Implementation

### Event Structure
Each event is structured with five distinct fields:
* **Event ID**: A unique identifier.
* **Event Type**: A description of the logged event.
* **Device/Sensor ID**: Identifies the generating hardware.
* **Timestamp**: Captured in a standard expected format.
* **Severity Level**: Categorized cleanly as `Low`, `Medium`, or `High`.

### Linked List Mechanics
* **Navigation**: Nodes contain pointers to both the previous and next nodes. The logger maintains distinct `head`, `tail`, and `current` pointers alongside a global record count, allowing flawless bidirectional navigation.
* **Complexity**: Tail insertion operates at a highly efficient \(O(1)\) time complexity.
* **Memory Management**: New nodes are dynamically allocated safely using `calloc()` and cleanly released via `free()`.
* **Capacity Management**: The system enforces a strict maximum capacity of **25 events**. If an event is added beyond this limit, the **oldest event is automatically removed** to accommodate the new record.

### Validation & Integrity
* **Duplicates**: Implements a case-insensitive validation check to reject duplicate Event IDs.
* **Normalization**: Severity values are systematically normalized for consistent string storage.
* **Input Checking**: Strict validation checks are applied to all required fields and timestamps.
* **Atomic Saving**: To minimize data corruption risks, records are saved to `events.log` utilizing a temporary file write followed by an atomic `rename()` process. This safeguards against incomplete saves overwriting data.

## Testing

The following scenarios were systematically tested to confirm logger stability:

| Test Case | Expected Result |
| :--- | :--- |
| Add valid event | Event is successfully stored in memory |
| Add duplicate event ID with same letter case | Duplicate entry is rejected |
| Add duplicate event ID with different letter case | Duplicate entry is rejected (case-insensitive) |
| Enter invalid severity | Input is cleanly rejected |
| Navigate forward and backward | The `current` event pointer updates correctly |
| Add more than 25 events | The oldest event is dropped automatically |
| Save events and inspect `events.log` | Saved records exactly match the current in-memory list |

## Limitations and Practical Application

### System Limitations
* **Startup Behavior**: In-memory events are not automatically reloaded from the file at initial execution startup.
* **Uniqueness Validation**: Duplicate identifier checks are restricted exclusively to current records resident in active memory.

### Practical Application Example
This application is perfectly suited for environments like a **manufacturing plant** to track events such as temperature sensor failures, cooling fan activations, or equipment overheating:

```text
[SCENARIO: Machine Temperature Exceeds Safe Threshold]
1. The system catches the threshold exception.
2. The logger records the Event ID, Sensor ID, Timestamp, and Severity.
3. Maintenance technicians can query the list to see exactly when the fault 
   occurred and instantly review all subsequent sequential events.
```
